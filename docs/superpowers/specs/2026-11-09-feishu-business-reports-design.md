# Daily and weekly business reports through Lark CLI

Status: approved to proceed by the owner on 2026-11-09.

## Intent and agreed scope

The owner requested daily and weekly eMAG operations reports, generated by
store-ops and delivered through the existing Lark CLI bot identity to the
owner's direct conversation. Hermes need not be running. Existing marketplace
write boundaries and collection scheduling remain authoritative.

## Approaches

1. **Selected by the owner:** store-ops builds deterministic reports and invokes
   the configured Lark CLI as bot. Reuses its credential store without copying
   app secrets into store-ops. Requires that CLI on the deployment machine.
2. Hermes schedules generation and delivery. Reuses its agent runtime, but adds
   an unnecessary availability dependency and complicates delivery receipts.
3. Separate webhook bot. Simple group delivery, but does not meet the selected
   existing-bot direct-message requirement.

## Proposed implementation

- Add a bounded report builder and CLI with preview, explicit send, and due
  report modes. Use existing immutable eMAG snapshots and report artifacts;
  never collect again merely to send a report.
- A private deployment JSON identifies store, CLI executable, expected app ID,
  recipient open ID, timezone, language and schedule. The CLI's own credential
  store remains authoritative. Validate expected app identity before delivery;
  fail closed on a mismatch. No new listener or externally reachable port.
- Generation runs on the laptop with the existing Windows identity and stable
  source installation. Delivery runs on Linux through the existing Hermes
  bot-only CLI adapter. A private fixed SSH argv per report kind fetches only
  the bounded generated report. SSH uses existing authentication; no new port,
  secret copy, marketplace collection or generic remote-command API is added.
  Do not change the existing supervisor's collection ownership or enable the
  old collector. A Linux user timer invokes due delivery periodically.
- Proposed defaults (builder choices): Europe/Bucharest business timezone;
  daily at 09:00 for the previous calendar day; Monday at 09:10 for the previous
  Monday-through-Sunday week; Chinese delivery. Startup catch-up is limited to
  the latest due daily and weekly periods. No historical message backlog.
- A durable per-store delivery ledger serializes overlapping invocations,
  stores the immutable prepared report before sending, and records recipient,
  app identity, period, snapshot and returned message ID. A deterministic CLI
  idempotency key is reused for the same prepared delivery. Unknown transport
  outcomes must not cause unbounded automatic resends after the API's dedupe
  window. In the first version, any timeout, crash after submission, or other
  uncertain outcome becomes `unknown` immediately and is never retried
  automatically. Retain it for explicit reconciliation; later periods may run.
- Enable the production reporting task only after preview review and one
  verified delivery to the selected owner's bot conversation.

## Evidence and content

- Headline, exact reporting period, capture time and freshness, available
  business figures, inventory observations, and up to three prioritized checks.
- Daily/weekly order and return counts come from dated raw projected evidence,
  deduplicated by source identity, not by summing rolling-window summaries.
  Prior-period comparisons require compatible evidence covering both periods.
- The collector explicitly says its API filter timezone is unverified. Treat
  naive record timestamps as ambiguous; do not silently assign Romania time or
  claim complete calendar-day sales. If timestamps/coverage cannot establish a
  period, show unavailable figures and clearly labeled captured-window context.
- No first-version revenue, GMV or net-profit promise: source prices, VAT,
  cancellations, refunds and currency need additional verified contracts.
  Never turn missing figures into zero or stock decreases into sales.
- Inventory is a point-in-time observation, not a historical period total.
  Comparisons name their snapshot baseline. Existing bounded issue diagnostics
  may supply review priorities without asserting a proven cause.
- Stale data produces a visibly stale report, not an apparent fresh success.
  Missing snapshots produce a data-unavailable report/receipt. No customer PII,
  credentials or unstructured source text is sent. Keep messages bounded and
  preserve full source references in local immutable report artifacts.

## Current findings and unresolved deployment identity

Both machines have Lark CLI, but their configured apps and corresponding owner
Open IDs differ. The owner's instruction to proceed is implemented using the
Linux Hermes bot-only adapter, with the Linux app's authenticated owner Open
ID. Bot readiness is not proof of delivery permission; verify the first send.
Do not transplant a user Open ID across apps or copy credentials.

Read-only inspection confirmed the Linux Hermes CLI adapter explicitly pins
its existing Linux app profile and forces bot identity. That adapter can be
reused as-is; it is distinct from the laptop's default Lark CLI app.

Builder review completed. The owner requested proceeding after the proposed
existing-bot integration; Linux Hermes is the stated implementation assumption.
